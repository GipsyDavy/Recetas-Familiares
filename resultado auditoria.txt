**6. Seguridad**

Hallazgos principales:

1. Alto: Desktop guarda access token y refresh token en `java.util.prefs`, no cifrado. El propio código lo reconoce en [AppSession.java](</C:/Users/GipsyDavy/MAVEN/Recetas Familiares/desktop/src/main/java/org/gipsybuho/recetasfamiliares/core/AppSession.java:8>) y persiste tokens en [AppSession.java](</C:/Users/GipsyDavy/MAVEN/Recetas Familiares/desktop/src/main/java/org/gipsybuho/recetasfamiliares/core/AppSession.java:69>).  
   Solución: Windows Credential Manager, macOS Keychain y libsecret/Linux Secret Service.

2. Alto: clientes usan HTTP por defecto. Android hardcodea `http://10.0.2.2:8080/` en [build.gradle.kts](</C:/Users/GipsyDavy/MAVEN/Recetas Familiares/android/app/build.gradle.kts:18>), iOS usa `http://localhost:8080/` en [ApiClient.kt](</C:/Users/GipsyDavy/MAVEN/Recetas Familiares/ios/composeApp/src/commonMain/kotlin/org/gipsybuho/recetasfamiliares/network/ApiClient.kt:16>) y Desktop `http://localhost:8080/` en [ApiClient.java](</C:/Users/GipsyDavy/MAVEN/Recetas Familiares/desktop/src/main/java/org/gipsybuho/recetasfamiliares/api/ApiClient.java:15>).  
   Solución: perfiles dev/prod separados, HTTPS obligatorio en prod y bloqueo de cleartext fuera de debug.

3. Medio/alto: `/uploads/**` es público en [SecurityConfig.java](</C:/Users/GipsyDavy/MAVEN/Recetas Familiares/backend/src/main/java/org/gipsybuho/recetasfamiliares/security/SecurityConfig.java:71>) y servido desde disco en [WebMvcConfig.java](</C:/Users/GipsyDavy/MAVEN/Recetas Familiares/backend/src/main/java/org/gipsybuho/recetasfamiliares/common/config/WebMvcConfig.java:19>). Las URLs son UUID, pero cualquier URL filtrada expone fotos familiares sin autorización.  
   Solución: servir imágenes mediante endpoint autenticado con ownership o usar URLs firmadas de corta duración.

4. Medio: validación de URLs de fotos permite `http://` y usa regex manual para hosts privados ([RecipePhotoService.java](</C:/Users/GipsyDavy/MAVEN/Recetas Familiares/backend/src/main/java/org/gipsybuho/recetasfamiliares/photos/RecipePhotoService.java:210>)). No es SSRF backend directo porque el backend no descarga esas URLs, pero los clientes sí pueden cargar imágenes remotas.  
   Solución: usar `URI`, normalización, allowlist o solo URLs propias generadas por upload.

5. Medio: iOS no tiene flujo de refresh automático. Guarda refresh token, pero `ApiClient` solo añade access token en `defaultRequest` ([ApiClient.kt](</C:/Users/GipsyDavy/MAVEN/Recetas Familiares/ios/composeApp/src/commonMain/kotlin/org/gipsybuho/recetasfamiliares/network/ApiClient.kt:25>)).  
   Solución: plugin Ktor que intercepte 401, rote refresh token y reintente una vez.

6. Bajo/medio: CSRF está desactivado ([SecurityConfig.java](</C:/Users/GipsyDavy/MAVEN/Recetas Familiares/backend/src/main/java/org/gipsybuho/recetasfamiliares/security/SecurityConfig.java:47>)). Es aceptable mientras solo se usen Bearer tokens en headers y no cookies, pero debe documentarse como decisión consciente. Si en futuro hay cookies, habrá que activar CSRF.

Auditoría Completa del Proyecto "Recetas Familia"
1. Visión General del Proyecto
"Recetas Familia" es una aplicación premium multiplataforma (Android, Desktop, iOS) diseñada para la gestión familiar de recetas, ingredientes, menús y memoria culinaria compartida. El proyecto busca ofrecer una experiencia cálida, moderna, premium, fluida y emocional, diferenciándose de aplicaciones corporativas o simples colecciones de recetas.
El ecosistema distribuido incluye:
•
Backend: Spring Boot (Java 21, MySQL, JWT, Spring Security).
•
Android: Nativo (Kotlin, Compose, Material You 3, Room, WorkManager).
•
Desktop: JavaFX (Maven).
•
iOS: Kotlin Multiplatform (KMP) + Compose Multiplatform (Ktor, SQLDelight, Keychain).
•
Base de Datos: MySQL principal, con sincronización multiplataforma y offline.
El proyecto se rige por principios de código mínimo viable, cambios quirúrgicos, priorización de UX, y una revisión constante de seguridad, calidad visual y experiencia de usuario.
2. Metodología de Auditoría
La auditoría se ha realizado siguiendo estrictamente las reglas y directrices establecidas en los documentos CLAUDE.md, README.md, Resumen.md e Interfaz.md. Se ha adoptado una perspectiva multidisciplinar, operando simultáneamente con los perfiles de:
1.
Desarrollador de software senior experto: Evaluando la corrección, limpieza, mantenibilidad y robustez del código.
2.
Diseñador gráfico e interfaces senior experto: Analizando la coherencia visual, el cuidado estético y la alineación con la identidad del producto.

El objetivo es presentar un diagnóstico detallado y proponer soluciones sin modificar ningún archivo del proyecto.

Estado General: El proyecto demuestra una fuerte conciencia de seguridad, con directrices explícitas y herramientas activas. Los sprints completados (Resumen.md) mencionan auditorías de seguridad y la invocación de VibeSec, con resultados de "BUILD SUCCESS" y "sin críticos/altos".
Puntos Fuertes:
•
Reglas Claras: CLAUDE.md establece reglas obligatorias para la revisión activa de vulnerabilidades en todo código tocado.
•
Herramientas Activas: El plugin security-guidance y las skills /VibeSec y /security-review se invocan automáticamente bajo condiciones específicas (autenticación, lógica de datos sensibles, APIs, etc.).
•
Autenticación Robusta: Uso de JWT, Refresh Tokens obligatorios, validación de ownership en todos los endpoints, y protección contra hardcoded secrets.
•
Anti-enumeración: Implementación de anti-enumeración en la invitación de miembros (Sprint 34+36 en Resumen.md).
•
Validación de Entradas: Validación de magic bytes para imágenes (JPEG/PNG/WebP) y sanitización de nombres de archivo.
•
OWASP Top 10: Mención explícita de aplicación de OWASP Top 10 en backend y seguridad general.
•
Mínimo Privilegio: Aplicación del principio de mínimo privilegio.
•
HSTS, CSP, CORS: Hardening HTTP en el backend.
Problemas Detectados / Áreas de Mejora:
•
Auditoría de Dependencias: Aunque no se menciona explícitamente, es crucial realizar auditorías periódicas de las dependencias de terceros (librerías, frameworks) para detectar vulnerabilidades conocidas (CVEs).
•
Secret Management: Aunque se prohíbe hardcoding, no se detalla la estrategia de gestión de secretos en producción (e.g., HashiCorp Vault, AWS Secrets Manager, Kubernetes Secrets). Se menciona variables de entorno obligatorias para credenciales de DB, lo cual es un buen inicio.

Logging y Monitorización: No se menciona una estrategia de logging de seguridad o monitorización de anomalías, lo cual es vital para detectar ataques en tiempo real.

Pruebas de Penetración: No se especifica si se realizan pruebas de penetración o auditorías de seguridad externas.
•
Seguridad en iOS/Desktop: Aunque se menciona Keychain para iOS y Windows Registry para Desktop, una revisión más profunda de las prácticas de seguridad específicas de cada plataforma (e.g., sandboxing, permisos de archivos, protección de datos en tránsito/reposo) sería beneficiosa.
Soluciones Propuestas:
•
Integrar Snyk/Dependabot: Para auditoría continua de dependencias.
•
Documentar Estrategia de Secretos: Detallar cómo se gestionan los secretos en entornos de producción.

Considerar Pruebas de Penetración: Realizar pruebas de penetración periódicas.

Revisión de Seguridad Específica por Plataforma: Asegurar que las mejores prácticas de seguridad para Android, Desktop e iOS se aplican consistentemente.

  Archivo:

  🔴 ALTO — S-2: Rate Limiter bypassable detrás de
  proxy inverso

  Archivo: backend/src/main/java/.../security/AuthRa
  teLimitFilter.java, línea 73
  String key = request.getRemoteAddr() + ":" +
  request.getRequestURI();

  Problema: El limitador de peticiones de auth usa
  getRemoteAddr() directamente. Si el backend se
  despliega detrás de un proxy inverso (nginx,
  Cloudflare, AWS ALB), getRemoteAddr() devolverá
  siempre la IP del proxy — no la IP del cliente
  real. Resultado: todos los usuarios comparten el
  mismo contador y el rate limit es trivialmente
  inefectivo para ataques de fuerza bruta.

  Riesgo: Brute force sin restricciones sobre
  /api/v1/auth/login y /api/v1/auth/register.

  Solución propuesta: Implementar extracción
  proxy-aware:
  String ip = Optional.ofNullable(request.getHeader(
  "X-Forwarded-For"))
      .map(h -> h.split(",")[0].trim())
      .orElse(request.getRemoteAddr());
  Con validación de que el proxy sea de confianza
  (lista blanca de IPs de proxy). Alternativamente,
  usar ForwardedHeaderFilter de Spring con
  configuración explícita de trusted proxies.

  warning para acciones destructivas. Eliminar es
  una acción destructiva correcta = warning, no
  error.

  ---
  5. PROBLEMAS ARQUITECTÓNICOS

  A-1: Instalador Desktop empaquetado con JDK-24 (no
  LTS)

  Archivo: CONTINUAR.md, sección Desktop v1.1

  El instalador fue compilado con C:\Program
  Files\Java\jdk-24 porque JDK-21 no estaba
  disponible. JDK-24 es una versión de soporte
  estándar (6 meses), no LTS. Para producción, el
  JRE embebido en el instalador debería ser JDK-21
  LTS (soporte hasta 2028).

  ---
  A-2: Rate limiter in-memory no escala
  horizontalmente

  Archivo: AuthRateLimitFilter.java

  El ConcurrentHashMap es local a la instancia JVM.
  Si se despliegan múltiples instancias del backend
  (o si la app se reinicia), los contadores se
  pierden. Para producción con más de 1 instancia:
  Redis como store compartido.

  ---
  A-3: No existe endpoint para que el usuario
  abandone voluntariamente una familia

  Un usuario puede ser expulsado por un ADMIN/OWNER,
  pero no puede abandonar una familia por su
  cuenta. No hay DELETE
  /api/v1/families/{id}/members/me.

  ---
  A-4: DevDataSeeder no actualiza password si el
  usuario ya existe

  Archivo: DevDataSeeder.java

  Si el usuario demo ya existe en la BD con un
  password diferente y se lanza el seeder, el seeder
  detecta que el usuario existe y no hace nada.
  Esto puede causar confusión en desarrollo si el
  password fue cambiado.

  Estado: Documentado en CONTINUAR.md.
